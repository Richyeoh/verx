# 复盘：这份设计合理吗

## 先自己挑刺

三端统一是不是伪命题。收敛点找得准才成立：统一的是 Registry 协议、包描述、命令，差异只漏在入口方式和平台杂务两处。如果以后发现第三处漏出来，说明收敛失败，宁可加一处平台适配，也不污染包描述。

去中心化会不会烂。Scoop 的教训是完全放开质量会碎。设计里用三件事兜：official Registry 守门加签名强制，搜索默认 official 优先，撤销名单加审计。开放和质量兼得的前提是默认安全，而不是默认信任。

包描述会不会不够用。声明式的好处是好写好审，代价是复杂包表达力弱。留的口子是受限模板加构建步骤声明，超大包允许拆分。原则是宁可包描述长一点，也不许写可执行逻辑。

依赖求解会不会过度。只取 Pacman 表达的子集，不做完整 SAT。够装常用软件、不把实现拖死是上限，冲突时能讲清原因比多解一个偏门版本重要。

无数据库撑不撑得住。撑得住，因为真相是文件，状态是缓存，事务靠日志。读写量小，并发只在入口切换处串行。目录上 `install/` 合并实体加状态，不再分两棵树，`registry/` 对远端 Registry，`bin/` 只放 Verx 自身，包入口另起 `shims/`，职责不打架。

库这条线会不会把 Verx 做重。不会，因为没另起 Registry、没另起命令：同一个 Registry 靠 `kind: app/lib` 区分，`install` 同一个，`app` 多一步写 `shims/`、`lib` 停在 `install/` 给编译器用。项目级只加 `verx.json + verx.lock + verx env/integrate`，学 vcpkg 但第一批只保 C/C++ native 库能编能找。风险在其它语言的集成口差异大，对策是不替构建系统包办，只保证 `include/lib/cmake/pkgconfig` 四件套加环境变量，找得到就行。

## 和四家的关系

没有为抄而抄的点。用户态和 shim 来自 Scoop 但解决了它的单端问题，双通道和命令动词来自 Homebrew 但扔掉了 Ruby 配方，事务和确认来自 Paru 但扔掉了 root 和双命令，库交付来自 vcpkg 但扔掉了只管 C/C++ 和 VS 绑定。每借一个优点，都对应扔掉它的一个代价，这份对应关系在第一篇里是能对上的。

## 待确认

- 方向：通用包管理器加去中心化 Registry，对吗。
- 命令：装升卸查锁体检服务，有没有要加要砍的。
- Registry：一个 Registry 概念，不分 bucket 和 tap，接受吗。
- 状态：纯文件无数据库，接受吗。
- 库：工具和库走同一个 Registry、靠 `kind: app/lib` 区分，`verx add/install/env/integrate + verx.json` 管项目依赖，第一批只保 C/C++，接受吗。

这五条点了头，就可以按 Registry、命令、架构的顺序起 Go 工程，先把 manifest 校验和装一个工具包、装一个库包跑通。
